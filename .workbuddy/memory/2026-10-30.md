## Music Fetch · 音乐下载前端（Cloudflare Worker）

- 需求：粘贴曲目信息文本 → 解析核心参数 → 提交后端 → 后端返回下载链接后在页面显示下载按钮；等待期间可继续提交，多任务排队、按顺序就绪。
- 方案（用户确认）：**Worker 代理转发**，页面只请求同源 `/api/process`，Worker 转发到真实后端，规避 CORS 并隐藏后端地址。
- 技术选型：TypeScript + 原生前端（无框架），HTML/CSS/JS 全部内联在 `src/page.ts | styles.ts | client.ts`，Worker 只做托管与代理，无静态资源目录。

### 结构
- `src/index.ts`：路由（`GET /`、`GET /api/config`、`POST /api/process`），代理含超时（`AbortSignal.timeout`）、Bearer 鉴权、错误映射（400/500/502/504）。
- `src/page.ts`：HTML 骨架 + 图标 + `window.__APP_CONFIG__` 注入。
- `src/client.ts`：浏览器脚本，用 `String.raw` 包裹（**内部禁用模板字面量与 `${`，避免转义/插值冲突**）；解析、并发队列、下载、aria2 推送、localStorage。
- `wrangler.jsonc`：`API_BASE_URL`/`API_TOKEN` 不放 vars（避免与 secret 同名冲突），只放 `API_PATH`、`ALLOW_API_OVERRIDE`、`API_TIMEOUT_MS`、`MAX_CONCURRENCY`。

### 关键实现决策
- 解析：按行 `标签: 值`（中英文冒号），标签白名单；多首拆分优先空行，无空行时按 `歌名：` 位置切分。`file_url` 必填。
- 下载：跨源预签名链接上 `a[download]` 会被浏览器忽略 → **fetch→blob 落盘优先，失败回退 `window.open`**，并提供「复制链接」。
- 有效期：从 URL 的 `X-Amz-Expires` 解析并倒计时，过期置灰并提供「重新生成」（复用原始文本 `raw`）。
- 安全：`ALLOW_API_OVERRIDE` 默认 `true` 供调试，生产必须 `false`，否则页面可指定任意后端地址（SSRF）。

### 追加：Aria2 JSON-RPC 批量下载
- 设置面板新增「Aria2 批量下载」分区：开关 + 端点/密钥/目录/Referer，配置存 `localStorage.prefs.aria`，**浏览器直连本机 aria2（不经过 Worker，云端 Worker 访问不到 localhost）**。
- JSON-RPC：`aria2.getVersion`（测试连接）、`aria2.addUri`；secret 以首个参数 `token:<secret>` 传入（`withSecret`）。
- `addUri` options：`out` = `标题 - 歌手.扩展名`（避免哈希命名）、可选 `dir`、`header: [Referer]`。
- 批量推送**串行执行**（避免瞬时灌入），通过后标记 `pushed/gid`，卡片显示「已加入 aria2」徽章；单曲可用 ⚡ 按钮单独推送；失败在消息行红字显示，retry 会重置 pushed。
- 必须要求 aria2 带 `--rpc-allow-origin-all` 启动，否则浏览器同源策略拦截；https 页面连 http://127.0.0.1 时 Safari 可能因混合内容拦截。
- 改进（用户要求）：移除「测试 Aria2 连接」按钮，改为**自动检测**——端点/密钥输入框停止输入 600ms 后、开关打开时、端点 blur 时，自动用 `currentAriaInput()` 读取页面实时值调用 `aria2.getVersion`，结果渲染到 `#aria-status` 状态条（成功绿/失败红/连接中 spinner）。
- `aria2Call(method, params, override)` 支持 override：自动检测传 override（即时输入），实际推送用已保存的 `aria`，两者互不干扰。
- 自动检测带 `ariaTestSeq` 序号防竞态：旧请求的回调被丢弃，避免慢响应覆盖新结果。

### 追加：duration 参数
- 需求：页面可接收 `duration`，有则传给后端（样例为秒，如 285）。
- 解析：新增标签 `时长/长度/时间/片长/duration/length/time`，RULES 用 `number: true` 分支走 `toSeconds()` 归一化。**不要在解析层面把时长当作忽略项**（原文档写的是忽略）。
- `toSeconds()`：`285` / `"285"` / `"07:07"` / `"1:02:03"` → 秒的整数；分段值除首段外必须 0–59（`12:99` 判无效）；无法识别返回 `''`。
- 传输：前端仅在有值时 `payload.duration = Number(...)`；`src/index.ts` 的 `toDuration()` 再做一次校验，**没有就整个字段不出现**（避免后端收到 null/0/空串）。
- 卡片 meta 与预览 chip 显示 `fmtTime()` 格式化后的时长。
- 附加支持了 JSON 输入（用户样例就是 JSON 数组）：`name→title`、`artist`（数组合并为 `甲, 乙`）、`album`、`url→file_url`、`pic→cover_url`、`duration`。注意该样例 `url` 为空 → 预览标红「缺少歌曲链接」并拒绝入队，这是预期行为。

### 追加：输入框自动入队 + 设置面板保存后收起（交互改成不去点按钮）
- 需求：输入框里被识别出的曲目**不用点「加入队列」**，直接落到页面下方列表；点「保存设置」后设置面板自动收回原位置。
- 实现（`client.ts`）：
  - 重构解析层：`songsFromJson()` 抽出 JSON 分支，`parseBlocks()` 抽出文本块分支，`parseText()` 组合二者；新增 `detectSongs(raw)` 返回 `{songs, blocks, missing}`，**带回曲目与原始文本块的对应关系**，是自动入队能「只挖走已入队文本」的关键。
  - `AUTO_DELAY=600ms` debounce（`scheduleAutoEnqueue` / `flushAutoEnqueue`），input 停止后自动 `autoEnqueue(false)`；⌘/Ctrl+Enter 与按钮走 `force=true`。
  - 自动模式判定：文本块**没有 `file_url` 视为没输完**，留在输入框继续等；补全后才进队，不弹错误 toast（避免打扰）。JSON 是整块无法按条切分 → 至少一条可入队才收走，全部缺链接（搜索结果场景）保留原文并靠预览 chip 标红。
  - `stripBlocks()`：从原文里 `indexOf` 挖掉已入队文本块后压缩多余空行（兼容 ES5，不用 trimEnd）；`caretToEnd()` 收尾光标。
  - 与原「填完即清空整个输入框」不同，现在只挖已识别部分，`updatePreview()` 后立即重算按钮 disabled 状态。
- 页面（`page.ts`）：按钮文案「加入队列」→「立即处理」，hint 改为「识别后自动进入下方队列 · ⌘Enter 立即处理」；`placeholder`、`settings-btn` 的 `aria-expanded/aria-controls` 同步更新。
- 设置面板：新增 `setSettingsOpen(open)` 统一控制 `.show` 与 `aria-expanded`，保存按钮回调末尾调用 `setSettingsOpen(false)`，保存即收起。
- 验证方式（本机无 node_modules，`tsc` 跑不了）：把 `client.ts` 当 ESM 导入后用 `new Function` 检查内联脚本语法，再用**最小 DOM/localStorage/window 桩**直接跑 CLIENT_JS，依次验：多首自动入队+残留保留、补全链接后进队、JSON 粘贴、缺链接 JSON 不误吞、设置展开→保存后收起。全部符合预期。图标常量（`ICON_X` 等）由 `page.ts` 注入，桩里需补齐。

### 追加：两段式提交（pending 状态）+ 并发只取环境变量
- 需求修正：**识别出来的曲目只进列表，不自动提交后台**，点「立即处理」才真正发请求；并发上限改成取环境变量，页面不再可改。
- 新增 `pending` 状态，任务生命周期 `pending → queued → running → done/error`：
  - `enqueue()` 落库时 status 用 `pending` 且**去掉末尾的 pump()**（这是"不自动提交"的唯一关键改动）。
  - `startPending()`：点按钮后把全部 pending 置 `queued` 并 pump。
  - `flushAutoEnqueue()` = 强制识别输入框剩余内容 + `startPending()`；自动防抖路径只调 `autoEnqueue(false)`。
  - `pump()` 天生只扫 `queued`，所以 pending 不会被后台请求带跑。
  - 配套：卡片徽章「待处理」、stats 增「待处理」计数、`save()` 过滤条件加 pending（刷新后仍等你点按钮）、`load()` 把历史 queued/running 统一降级为 pending、`clearFinished()` 保留 pending。
  - 按钮状态抽成 `refreshSubmit()`：有 pending **或** 输入框有可处理内容才 enabled，label 动态显示「立即处理 (N)」；由 `updatePreview()`（记录 `inputHasSongs`，用 `detectSongs` 判定而非 `parseText`，因为缺链接的条目不该点亮按钮）和 `renderStats()` 共同驱动。
  - 预览仍用 `parseText()`，保留「缺少歌曲链接」红 chip 反馈。
- **并发（最终口径）**：环境变量 `MAX_CONCURRENCY` 是**上限**，页面**可以改**、但只能在 `1 ~ 上限` 之间。
  - `client.ts`：`concLimit = clampInt(CONFIG.maxConcurrency, 1, 10, 2)`；`concurrency = clampInt(prefs.concurrency || concLimit, 1, concLimit, concLimit)`，本地值越界会被收敛。
  - 保存设置时再 clamp 一次并回写输入框；`wanted > concLimit` 时 toast「并发数超过环境变量上限 N，已按上限处理」（用报错样式，替代常规的「设置已保存」）。
  - `index.ts` / `page.ts` 的 env clamp 仍是 `1–10`（环境变量本身的合法范围）；页面输入框 `min=1 max=<env值>`，label 写「最大并发处理数（1–N）」，client 启动时用 prefs 值覆盖 `value`。
  - **不要给环境变量本身封顶**：最初写成 `clampInt(env.MAX_CONCURRENCY, 1, 10, 2)`，导致 env=20 时页面最高只有 10（用户明确指出这是 bug）。正确做法是把上限口径交给环境变量：新增导出的 `concurrencyLimit(value)`（只做 `parseInt`，`NaN` 或 `<1` 才回落到 2，**无上限**），`page.ts` 与 `index.ts` 共用它（`index.ts` 的 `clampInt` 仍留给 `API_TIMEOUT_MS`）；前端 `concLimit = clampInt(CONFIG.maxConcurrency, 1, Number.MAX_SAFE_INTEGER, 2)`。页面可调节范围 = `1 ~ MAX_CONCURRENCY`。
  - 因 `tsconfig` 开了 `noUnusedLocals`，删掉 `page.ts` 里失活的 `clampInt` 否则 tsc 报 TS6133。
  - 历史：中途曾按「页面不可改」做成 readonly 并删掉 `el.concInput`，随后用户改回可编辑 → `el.concInput` 与 prefs 读写全部恢复。**这类"能不能手动改"的需求容易反复，改动前先确认是要"禁用"还是"加上限"。**
- 验证：DOM 桩 env=20 三场景 —— 无本地设置/页面设 20 → 并发峰值 20；页面设 25 → 收敛到 20 并提示；env=3 → 峰值 3；25 首任务全部完成。`concurrencyLimit` 真源码取值：未设置/空/abc/0/-3 → 2；1/2/10/20/999 → 原值不截断。`npm run typecheck` 通过；`wrangler deploy --dry-run` 构建成功（75.82 KiB / gzip 22.93 KiB）。
- 环境备注：本机原本没有 node_modules（`npm run typecheck` 报 command not found），已用 `npm install --no-save` 装好依赖，未改动 package.json / package-lock.json。
- 验证（同一套 DOM 桩跑真实 CLIENT_JS，env=5 四种情况）：无本地设置→并发 5；本地设 2→并发 2；本地设 50（越界）→收敛到 5；页面手动改 8 保存→回写 5 并提示。并发峰值用「同时 inflight 请求数」观测，6 首任务全部跑完请求总数为 6。
